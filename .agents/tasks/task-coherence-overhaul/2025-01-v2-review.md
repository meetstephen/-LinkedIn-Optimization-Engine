All five issues from the v1 review have been addressed: scheduler pipe receiver added, hook/comment example helpers wired into production, 13 tests added for `_predict_engagement`, MD5 seeding applied in all modules, geo markers generalized. **Watch for:** The scheduler pipe receiver sets `scheduler_prefill` in session state but no downstream widget in `render_content_scheduler()` ever reads that key — the user sees a success banner but the piped content is silently lost (confirmed). ## High-level view

The scheduler pipe is partially wired — the sender in `post_generator.py` and the receiver pop in `app.py` both exist, but the receiver stashes the content in `scheduler_prefill` without any widget consuming that key. The scheduler's UI works exclusively from Library posts fetched via `_db.get_schedule()`, so the piped content has no path to the user's screen beyond the success toast.

The proper noun detection fallback addresses the v1 geo-coupling concern but trades it for a different problem: any capitalized word mid-sentence (brand names, app names, personal names) triggers the specificity bonus. This is a low-severity scoring inaccuracy — it means the specificity factor will almost always score at least 7/20, reducing its discriminating power for posts that genuinely lack specificity.

## Incomplete scheduler pipe: receiver exists but has no consumer

The fix adds lines 2937-2940 in `app.py`:

```python
_piped_scheduler = st.session_state.pop("scheduler_pipe_content", None)
if _piped_scheduler:
    st.session_state["scheduler_prefill"] = _piped_scheduler
    st.success("✅ Post received from Post Generator — ready to schedule below.")
```

This correctly pops the pipe key and avoids the silent accumulation problem from v1. But `scheduler_prefill` is never referenced again — not by any `st.text_area(value=...)`, not by any scheduling logic. The scheduler loads its posts exclusively from `_db.get_schedule()` (line 2992), which fetches from Supabase. There's no path from `scheduler_prefill` to the weekly grid.

The practical result: user clicks "Schedule" in Post Generator, lands on the Scheduler page, sees the green success banner, and then has no way to act on the piped content from that page. They'd need to go back, save to Library, then schedule from Library — the same flow they'd use without the pipe button.

## Proper noun fallback in specificity scoring

The expanded `known_places` list (16 cities) handles the most common case. For posts mentioning unlisted places, the fallback scans for any capitalized word that isn't the first word of a sentence:

```python
for w in words[1:]:
    if w and w[0].isupper() and len(w) > 1 and w.isalpha():
        _has_proper_noun = True
        break
```

This catches "Bangalore", "Johannesburg", "Accra" — but also "Python", "CEO", "Apple". The `isalpha()` guard filters out "N4M" and mixed-case brands like "WhatsApp" (contains no non-alpha in each word — actually "WhatsApp" does pass `isalpha()`). Most brand names and personal names pass through.

The scoring impact is +2 out of 20, so it won't mislead users materially. But it means the specificity factor will almost always hit at least 7 (baseline 5 + 2 for any post containing a proper noun mid-sentence), reducing the signal for posts that genuinely lack concrete details.
